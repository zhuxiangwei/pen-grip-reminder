# 摄像头分辨率探测 + 窗口应用

## 1. 摄像头最高分辨率探测

**结论：本机摄像头（DSHOW 后端）的硬件上限就是 `1280x720`。**

### 1.1 探测过程（`tools/probe_camera.py`）

逐个请求分辨率，**回读实际值** + 取首帧确认真实尺寸：

```
请求         回读(W/H属性)   首帧实际      判定
3840x2160   1280x720        1280x720      ⬇ 降级
1920x1080   1280x720        1280x720      ⬇ 降级
1600x1200   1280x720        1280x720      ⬇ 降级
1440x1080   1280x720        1280x720      ⬇ 降级
1280x960    1280x720        1280x720      ⬇ 降级
1280x720    1280x720        1280x720      ✅ 支持
1024x768    960x540         960x540       ⬇ 降级
960x720     960x540         960x540       ⬇ 降级
960x540     960x540         960x540       ✅ 支持
848x480     848x480         848x480       ✅ 支持
800x600     848x480         848x480       ⬇ 降级
640x480     640x480         640x480       ✅ 支持
640x360     640x360         640x360       ✅ 支持
320x240     320x240         320x240       ✅ 支持
```

**关键教训**：请求 1080p / 2K / 4K，**驱动不报错、直接静默降级到 720p**。
如果不回读实际值，就会以为在用 1080p、而实际一直在 720p 跑 ——
「手宽 ≥200px」这条门槛是按真实像素算的，分辨率弄错门槛就整个失效。

### 1.2 后端差异

- **DSHOW**：最高 1280x720，实测吞吐 28.9 fps
- **MSMF**：同样上限 1280x720，但**重复开流会永久卡死**（卡在 `VideoCapture`
  构造里，连 KeyboardInterrupt 都进不去，只能 SIGTERM 杀掉）
  → 工具里用**子进程 + 8s 超时**隔离它，避免拖垮整个探测

### 1.3 帧率与推理耗时

```
实测吞吐（DSHOW @1280x720）：40 帧 / 1.38s = 28.9 fps

MediaPipe 单帧推理耗时 vs 输入分辨率：
  1280x720   中位 18.5 ms  → 上限 54 fps
   960x540   中位 18.9 ms  → 上限 53 fps
   848x480   中位 18.7 ms  → 上限 54 fps
   640x480   中位 19.7 ms  → 上限 51 fps
   320x180   中位 17.7 ms  → 上限 56 fps
```

**最重要的发现**：MediaPipe 内部会把输入缩到约 224px，所以
**降分辨率不会更快** —— 720p 18.5ms vs 320x180 17.7ms，差不到 1ms。
→ 没有任何理由降分辨率。全流程统一用硬件上限，信息量最大化。

### 1.4 配置落点

探测结果写入 `pen_grip_config.json` 的 `camera` 段：

```json
{
  "camera": {
    "index": 0, "backend": "DSHOW",
    "width": 1280, "height": 720,
    "max_width": 1280, "max_height": 720,
    "supported": ["1280x720","960x540","848x480","640x480","640x360","320x240"],
    "inference_ms": {...}
  }
}
```

**全流程统一从这个配置读分辨率**（`pg_utils.camera_size()`），保证：
实时预览 / 盲录 / 录像分析 / 窗口应用 **都用一个分辨率**，
「手宽 ≥200px」的门槛在任何环节含义一致。

## 2. 窗口应用（`app.py`）

### 2.1 为什么是 tkinter 不是 PySide6

PySide6 / PyQt5 / PyQt6 **全没装**（实测三选全 NO）。tkinter 是 Python 自带。
这个项目依赖已经不少（opencv + mediapipe + matplotlib），窗口本身没必要
再拉一个 100MB+ 的 Qt。**零新增依赖**对「双击就能用」很重要。

### 2.2 核心原则：不重写检测逻辑

所有指标、视角门控、手别选择、阈值对照**全部复用** `grip_metrics` /
`hand_probe` 里的现有函数。窗口只是套了个界面。
两份实现会随时间漂移 —— 改一处忘另一处是最常见的坑。

复用点：
- `pg.open_camera_auto()` —— 分辨率/后端/索引从配置读
- `hp.make_hand()` —— 同一个 HandLandmarker
- `gm.compute_grip_metrics()` —— 同一套指标
- `gm.view_quality()` / `gm.palm_view_verdict()` —— 同一套门控
- `hp.HandSelector` / `hp.Recorder` —— 同一套手别选择 + 样本记录
- `hp.draw()` —— 同一套画面标注（含双手 + 放大镜）

### 2.3 界面布局

```
┌─────────────────────────────┬───────────────────────┐
│                             │  机位体检             │
│        摄像头画面            │   手宽 / 视角角 / 稳定性│
│      （含手部特写标注）        │                       │
│                             │  样本计数             │
│                             │   正确 / 包食指 / 其他 │
│                             │                       │
│                             │  [1] 正确握笔         │
│                             │  [2] 拇指包食指        │
│                             │  [3] 其他错误          │
│                             │                       │
├─────────────────────────────┤  [出对照表]           │
│ [ 开始 ] [ 冻结 ] [ ↵ 出表 ] │  [保存样本]           │
└─────────────────────────────┴───────────────────────┘
```

### 2.4 按键（和命令行版一致，肌肉记忆可复用）

| 键 | 作用 |
|----|------|
| `1` / `2` / `3` | 记录当前帧为 正确握笔 / 拇指包食指 / 其他错误 |
| `z` | 开关拇指-食指放大镜 |
| `[` / `]` | 锁定被测手 = 画面左半 / 右半（不看"左右手"，只看画面位置） |
| `\` | 取消锁定，回到自动（按运动量猜） |
| `空格` | 冻结 / 继续画面 |
| `p` | 出对照表（等价于点按钮） |
| `w` | 保存样本到磁盘 |
| `q` / `Esc` | 退出 |

### 2.5 运行

```
双击  窗口应用.bat
# 或
envs\pg\Scripts\python.exe app.py
# 指定摄像头：
envs\pg\Scripts\python.exe app.py --camera 1
```

### 2.6 验证

- `py_compile` 语法通过
- 真实构造 + 4 秒 live 主循环：err=None，面板正常刷新
- 用一张含手的静止帧喂 `_loop`：检测→指标→面板整条链路通
  （px_w=137 / 视角角=111° / thumb_side=-0.45 / thumb_index_dist=0.299，面板显示一致）
- ⚠️ 窗口应用目前没在「真实握笔 + 挪近机位」下跑过，
  那个得用户实机双击验证（环境里我能验证代码和链路，验证不了真人握笔姿势）
